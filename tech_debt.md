### 📐 Архитектурный план: Lead-Lag Momentum Engine (v9.1)

#### 1. Концепция: Торговля СТРОГО Кейса Б (Опережающий Импульс Поводыря)
* **Запрещен Кейс А (Обе биржи в хаотичном движении):** Высокий риск ложного арбитража.
* **Категорически запрещен Кейс В (Движение на ведомой бирже):** Попытка ловить падающие ножи или заходить против локального давления стакана.
* **Разрешен ТОЛЬКО Кейс Б:** 
  1. Биржа-Поводырь (Binance) совершает резкий направленный импульс: $|\Delta_{oracle}| \ge \delta_{min}$ за последние $T_{window}$ миллисекунд (например, $\ge +0.25\%$ за 200 мс).
  2. Биржа-Мишень (Bitget/KuCoin) еще **находится в покое**: $|\Delta_{target}| \le \delta_{max}$ (например, не более $\pm 0.05\%$).
  3. Суммарный чистый спред после учета комиссий и локального bid/ask спреда удовлетворяет `spread_entry`.

#### 2. Объектно-ориентированная архитектура (ООП по Протоколу разработки)
Создается выделенный независимый модуль `CORE/impulse_detector.py` с классом `ImpulseDetector`:
* **Заголовок:** `# FILE: CORE/impulse_detector.py` / `# ROLE: ...`
* **Инициализация:** Прямое чтение параметров `cfg["trading_rules"]["entry"]["impulse_detector"]` без `.get()`.
* **Хранилище тиков:** Двусторонние очереди `collections.deque` с метками времени высокого разрешения `time.monotonic_ns()`.
* **Подавление фантомных тиков:** Расчет дельты не по 1-му уровню стакана (который можно спуфить 1 контрактом), а по средневзвешенной цене VWAP первых 3 уровней стакана.

```python
# ============================================================
# FILE: CORE/impulse_detector.py
# ROLE: Lead-lag momentum and impulse verification engine for Oracle-Target pairs.
# ============================================================
from collections import deque
import time
from typing import Dict, Tuple, Optional

class ImpulseDetector:
    def __init__(self, cfg: dict):
        impulse_cfg = cfg["trading_rules"]["entry"]["impulse_detector"]
        self.is_enabled = bool(impulse_cfg["enabled"])
        self.buffer_window_sec = float(impulse_cfg["buffer_window_ms"]) / 1000.0
        self.oracle_min_delta = float(impulse_cfg["oracle_min_delta_pct"])
        self.target_max_delta = float(impulse_cfg["target_max_delta_pct"])
        
        # Хранилище тиков: (symbol, exchange) -> deque of (timestamp_mono, price)
        self._buffers: Dict[Tuple[str, str], deque] = {}

    def update(self, sym: str, ex: str, vwap_price: float, ts_mono: float):
        key = (sym, ex)
        if key not in self._buffers:
            self._buffers[key] = deque()
        buf = self._buffers[key]
        buf.append((ts_mono, vwap_price))
        
        # Очистка устаревших тиков за пределами окна
        cutoff = ts_mono - self.buffer_window_sec
        while buf and buf[0][0] < cutoff:
            buf.popleft()

    def get_delta(self, sym: str, ex: str, current_price: float) -> float:
        key = (sym, ex)
        buf = self._buffers.get(key)
        if not buf or len(buf) < 2:
            return 0.0
        base_price = buf[0][1]
        if base_price <= 0:
            return 0.0
        return (current_price - base_price) / base_price

    def check_impulse(
        self,
        sym: str,
        oracle_ex: str,
        target_ex: str,
        side: str,
        oracle_price: float,
        target_price: float
    ) -> Tuple[bool, str, float, float]:
        """
        Проверяет соблюдение Кейса Б:
        - Для LONG: Oracle вырос >= +oracle_min_delta, Target изменился не более target_max_delta
        - Для SHORT: Oracle упал <= -oracle_min_delta, Target изменился не более target_max_delta
        """
        if not self.is_enabled:
            return True, "IMPULSE_DISABLED", 0.0, 0.0
            
        o_delta = self.get_delta(sym, oracle_ex, oracle_price)
        t_delta = self.get_delta(sym, target_ex, target_price)
        
        if side == "LONG":
            if o_delta < self.oracle_min_delta:
                return False, f"ORACLE_NO_MOMENTUM ({o_delta*100:+.2f}% < {self.oracle_min_delta*100:+.2f}%)", o_delta, t_delta
            if abs(t_delta) > self.target_max_delta:
                return False, f"TARGET_NOT_STATIC ({abs(t_delta)*100:+.2f}% > {self.target_max_delta*100:+.2f}%)", o_delta, t_delta
        else: # SHORT
            if o_delta > -self.oracle_min_delta:
                return False, f"ORACLE_NO_MOMENTUM ({o_delta*100:+.2f}% > -{self.oracle_min_delta*100:+.2f}%)", o_delta, t_delta
            if abs(t_delta) > self.target_max_delta:
                return False, f"TARGET_NOT_STATIC ({abs(t_delta)*100:+.2f}% > {self.target_max_delta*100:+.2f}%)", o_delta, t_delta
                
        return True, "VALID_IMPULSE_CASE_B", o_delta, t_delta
```

### 🛡️ Рефакторинг v9.1: Детектор Стояка (StaticDetector) и Возврат Глубокой Математики Входа (evaluate_entry)

#### 1. Пост-мортем: Ловушка ложного спреда (Инциденты BTW -3.29% и FLOCK -2.90%)
* **Симптом:** Бот заходил в LONG на ведомой бирже (Bitget), после чего цена не росла вслед за Оракулом (Binance), а стремительно обваливалась, вызывая максимальный убыток и бан монеты.
* **Коренная причина:** Классическая формула спреда `(Oracle - Target) / Oracle` математически слепа к источнику расширения спреда:
  - **Кейс Б (Истинный опережающий арбитраж):** На Binance произошел всплеск спроса (памп), а маркет-мейкеры Bitget еще не успели переставить котировки. Target стоит на месте. Это валидный вход.
  - **Кейс В (Локальный дамп / Падающий нож):** На Bitget крупный участник продавил стакан вниз, а на Binance цена осталась неизменной. Формула спреда выдает положительный сигнал $\ge 1.5\%$, и бот покупает падающий нож прямо под агрессивным продавцом.
* **Ликвидация избыточной магии параметров:**
  Предыдущая попытка внедрить детектор импульса содержала несогласованные параметры (`oracle_min_delta`, `target_max_delta`, `max_static_leg_ratio`) на разных масштабных шкалах. Они создавали скрытые конфликты с базовым порогом `spread_entry_base`.
* **Решение: Детектор Стояка (`StaticDetector`) с 4 чистыми параметрами:**
  Вместо замера импульса на обеих ногах система изолированно следит за **статичной ногой** (`static_leg`):
  1. `enabled`: включение детектора (`true`).
  2. `static_leg`: `'TARGET'` (для Кейса Б, когда импульс идет на Оракуле, а Мишень должна стоять) или `'ORACLE'` (для Кейса В).
  3. `max_static_leg_pct`: допустимый коридор отклонения цены ноги от своего скользящего среднего (`0.0020` = 0.2%).
  4. `buffer_window_sec`: ультракороткое скользящее окно накопления тиков (`0.25` = 250 мс, ~5–8 тиков при поступлении WS-стаканов каждые 30–50 мс).

#### 2. Математика расчета стояка (Top-3 Mid Price, C-Level Buffer & Защита от «Резинового Буфера»)
* **Низкоуровневая реализация на Си в CPython:**
  - Буферы цен и меток времени разделены на независимые очереди `_price_buffers` и `_ts_buffers` типа `collections.deque` (`Modules/_collectionsmodule.c`).
  - Подрезка хвостов старше `buffer_window_sec` выполняется через C-функцию `deque_popleft` со сложностью $O(1)$ без аллокаций памяти.
  - Расчет среднего арифметического накопленного ряда цен:
    $$\bar{P} = \frac{1}{N} \sum_{i=1}^N P_i$$
    выполняется напрямую на уровне Си через `math.fsum(price_buf)` (`Modules/mathmodule.c:math_fsum_impl`). Функция использует точный алгоритм Шеучука (Shewchuk) с промежуточными суммами без погрешностей округления IEEE 754 и полностью исключает генераторы и байткод-циклы Python.
* **Защита от «Резинового Буфера» (Карантин-кулдаун на окно `buffer_window_sec`):**
  - **Проблема:** Если стоячая нога сдвинулась ($\delta > \text{max\_static\_leg\_pct}$), аномальный тик попадает в буфер. Пока этот тик находится в буфере вперемешку со старыми ценами, среднее арифметическое $\bar{P}$ становится искаженным («резиновым»), порождая ложные срабатывания и преждевременные входы до стабилизации рынка.
  - **Решение:** При фиксации $\delta > \text{max\_static\_leg\_pct}$ метод `is_leg_static` взводит жесткий кулдаун ровно на длительность окна:
    $$\text{cool\_off\_until} = t_{\text{mono}} + \text{buffer\_window\_sec}$$
  - На протяжении всего окна `buffer_window_sec` (250 мс) метод `is_leg_static` возвращает `False` (`LEG_COOLING_OFF`), блокируя любые входы.
  - В это время фоновый стрим через `update` продолжает вхолостую накапливать поступающие тики, естественным образом вымывая через `popleft()` все устаревшие цены до момента аномалии.
  - По истечении ровно `buffer_window_sec` в буфере остаются строго новые, однородные котировки post-anomaly периода. Только тогда стояк может быть подтвержден заново.

# Архитектурный план: Модернизация StaticDetector (v10)

## Описание задачи и проблематика

### 1. Реструктуризация конфигов
Перемещение секции `static_detector` внутрь `signal_filters` во всех профилях бирж (`cfg.json`) и в движке (`CORE/trading_engine.py`), так как детектор стоячей ноги концептуально является составной частью фильтрации сигналов входа.

### 2. Проблема ложного отсечения при когерентном движении («Гуськом» + волатильность)
* **Текущая механика:** `StaticDetector` накапливает цены одной ноги в `deque` за окно `buffer_window_sec` (например, 350 мс) и сравнивает текущую цену со средним арифметическим буфера: $\text{dev} = \frac{|P - \bar{P}|}{\bar{P}}$. При превышении порога `max_static_leg_ratio` (0.20%) взводится карантин-кулдаун на 350 мс (`LEG_COOLING_OFF`), полностью блокирующий проверки.
* **Проблема:** На высоковолатильном рынке цены обеих ног (Oracle и Target) могут стремительно двигаться вместе «гуськом» (синхронный рыночный тренд / когерентный дрейф). Спред между ними равен 0.0%. Однако из-за быстрого движения стоячая нога превышает `max_static_leg_ratio` относительно своих старых цен в буфере и уходит в кулдаун. Когда же одна из ног стреляет (создавая истинный арбитражный спред, например +0.8%), система отклоняет валидный вход, так как стоячая нога либо уже заблокирована в кулдауне, либо ее текущая цена отклонена от исторического среднего 350-миллисекундного буфера.

### 3. Инвариантность Кейсов Б и В (`static_leg == TARGET & ORACLE`)
* **Кейс Б (Lead-Lag Momentum):** Поводырь (Oracle) резко выстрелил, Мишень (Target) стоит на месте. Входим на Target в сторону импульса Oracle.
* **Кейс В (Mean-Reversion / Liquidity Hole):** Поводырь (Oracle) стоит на месте (якорь), Мишень (Target) локально продавили / выбили стакан. Входим на Target в сторону возврата к Oracle.
* **Кейс А (Хаос):** Обе биржи двигаются хаотично/рассинхронизированно — вход категорически запрещен.
* **Цель:** Поддержать в конфиге значение `static_leg: "ANY"` (или `["TARGET", "ORACLE"]`), позволяющее системе динамически определять, какой из идеальных кейсов (Б или В) сформировался, и входить при соблюдении покоя соответствующей ноги.

## Варианты решения проблемы «Гуськом» и детерминации Кейсов Б/В

### Вариант 1 (Рекомендуемый): Трекинг спокойного базиса (Quiescent Baseline Tracking / Pre-Spread Anchor)

#### Механика:
1. **Фоновое состояние (Спреда нет / «Гуськом»):**
   Пока чистый спред между биржами находится в пределах фонового шума ($|\text{spread}| < \text{spread\_entry\_pre}$), обе ноги считаются находящимися в когерентном движении. Система непрерывно обновляет предсигнальный базис цен:
   $$P_{\text{oracle}}^{\text{base}} = P_{\text{oracle}}(t), \quad P_{\text{target}}^{\text{base}} = P_{\text{target}}(t), \quad t^{\text{base}} = t_{\text{mono}}$$
2. **Фиксация базиса при выстреле спреда:**
   Как только спред начинает расширяться ($\ge \text{spread\_entry\_pre}$):
   Базис замораживается на время импульса (окно `buffer_window_sec`, например 350 мс).
3. **Замер чистых смещений обеих ног относительно базиса:**
   $$\Delta_{\text{oracle}} = \frac{|P_{\text{oracle}} - P_{\text{oracle}}^{\text{base}}|}{P_{\text{oracle}}^{\text{base}}}$$
   $$\Delta_{\text{target}} = \frac{|P_{\text{target}} - P_{\text{target}}^{\text{base}}|}{P_{\text{target}}^{\text{base}}}$$
4. **Классификация кейса:**
   * **Кейс Б (Target статичен, Oracle улетел):**
     $$\Delta_{\text{target}} \le \text{max\_static\_leg\_ratio} \quad \text{И} \quad \Delta_{\text{oracle}} > \text{max\_static\_leg\_ratio}$$
     $\implies$ **ВХОД РАЗРЕШЕН (Кейс Б)**.
   * **Кейс В (Oracle статичен, Target улетел):**
     $$\Delta_{\text{oracle}} \le \text{max\_static\_leg\_ratio} \quad \text{И} \quad \Delta_{\text{target}} > \text{max\_static\_leg\_ratio}$$
     $\implies$ **ВХОД РАЗРЕШЕН (Кейс В)**.
   * **Кейс А (Обе ноги двигаются / хаос):**
     $$\Delta_{\text{target}} > \text{max\_static\_leg\_ratio} \quad \text{И} \quad \Delta_{\text{oracle}} > \text{max\_static\_leg\_ratio}$$
     $\implies$ **ОТКЛОНЕНО (Кейс А — обе ноги нестабильны)**.

#### Преимущества:
- **100% иммунитет к совместному тренду («гуськом»):** Не имеет значения, пролетел ли рынок 0.5% или 2.0% за последние полсекунды. Если спред был около нуля, базис плавно сопровождал рынок. Дельта считается строго от момента расхождения спреда.
- **Исключение ложных кулдаунов:** Устраняется разрушительный безусловный кулдаун, парализующий торговлю при обычном рыночном тренде.
- **Ультрабыстродействие $O(1)$:** Никаких тяжелых поисков по декам, чистая арифметика на уровне регистров процессора (< 1 микросекунды).
- **Прозрачность в телеметрии и логах:** Движок прямо сообщает в логе: `[CASE_B_OK] Target delta: 0.02% <= 0.20%, Oracle delta: 0.75% > 0.20%` или `[CASE_C_OK] Oracle delta: 0.01% <= 0.20%, Target delta: 0.80% > 0.20%`.

---

### Вариант 2: Дифференциальный анализ скорости на микро-окне (Micro-Window Velocity Delta)

#### Механика:
- Замерять векторную скорость изменения цены ног за ультракороткое микро-окно (например, 50–100 мс) непосредственно перед сигналом:
  $$V_{\text{target}} = \frac{|P_{\text{target}}(t) - P_{\text{target}}(t - \tau)|}{P_{\text{target}}(t - \tau)}$$
  $$V_{\text{oracle}} = \frac{|P_{\text{oracle}}(t) - P_{\text{oracle}}(t - \tau)|}{P_{\text{oracle}}(t - \tau)}$$
- Если за последние $\tau$ мс целевая нога не совершала резких движений ($V_{\text{target}} \le \text{threshold}$), она признается статичной.

#### Недостатки:
- Сильная зависимость от калибровки $\tau$: если импульс длится 150 мс, окно 80 мс может захватить лишь часть движения или пропустить начало.
- Асинхронность тиков: на разных биржах WebSocket шлет обновления с разной частотой (например, на Bitget тики могут приходить раз в 80–120 мс, а на Binance раз в 20–30 мс). Попадание в интервал между тиками дает ложную нулевую скорость.

---

### Вариант 3: Относительный спредовый Z-Score (Spread-Ratio Detrending)

#### Механика:
- Нормализовать цены ног через отношение $R(t) = P_{\text{oracle}}(t) / P_{\text{target}}(t)$.
- Вычитать синфазную компоненту через скользящий Z-score отношения спреда.

#### Недостатки:
- Оверинжиниринг: появление абстрактных математических коэффициентов, оторванных от реальных процентов и долей цены.
- Сложность конфигурирования для оператора (нарушение пункта 5 Протокола разработки).

## Детали проектирования конфигурации и API

### 1. Формат в `cfg.json`
`static_detector` переносится внутрь `signal_filters`. Поддерживаются режимы `TARGET`, `ORACLE`, `ANY` (или список `["TARGET", "ORACLE"]`):

```json
"signal_filters": {
    "static_detector": {
        "enabled": true,
        "enabled_desc": "Включение детектора стоячей ноги. Блокирует вход, если стоячая нога отклоняется от предсигнального базиса.",

        "static_leg_desc": "Стоячая нога: 'TARGET' (Кейс Б: Оракул летит, Мишень стоит); 'ORACLE' (Кейс В: Мишень летит, Оракул стоит); 'ANY' (инвариантный режим: разрешены и Кейс Б, и Кейс В).",
        "max_static_leg_ratio": 0.0020,
        "max_static_leg_ratio_desc": "Максимально допустимое относительное смещение стоячей ноги от базиса в долях от 1 (0.0020 = 0.20%).",
        "buffer_window_sec": 0.35,
        "buffer_window_sec_desc": "Окно удержания предсигнального базиса и очистки тиков (сек). 0.35 с = 350 мс."
    },
    "spread_entry_pre": [0.008, 0.05],
    "spread_entry_base": 0.006,
    "min_top_depth_usd": 40.0,
    "min_signal_dwell_ms": 0,
    "top_n_candidates": 4,
    "orderbook_imbalance": { ... },
    "synthetic_exit": { ... }
}
```

### 2. Поведение при `static_leg`:
* `"TARGET"`: Строго Кейс Б. Если Target сместился $> \text{max\_static\_leg\_ratio}$, сигнал отклоняется, даже если Oracle стоял.
* `"ORACLE"`: Строго Кейс В. Если Oracle сместился $> \text{max\_static\_leg\_ratio}$, сигнал отклоняется, даже если Target стоял.
* `"ANY"` (или `["TARGET", "ORACLE"]`): Инвариантный режим. Если хотя бы одна из ног сохраняет покой ($\le \text{max\_static\_leg\_ratio}$), а вторая обеспечивает импульс спреда, сигнал принимается с указанием сработавшего кейса (`CASE_B` или `CASE_C`). Если обе ноги сместились (Кейс А) — отклоняется с причиной `REJECTED_CASE_A_BOTH_LEGS_MOVING`.

### 🛡 Ветка v11.0: Нейтрализация трех фундаментальных мин слива депозита & Orderbook Hunting

#### 1. Устраненные критические дефекты микроструктуры
* **Мина №1 (Ловушка Кейса В / Falling Knives):**
  * *Проблема:* Разрешение входа при локальных проливах на Target (`static_leg: "ANY"`, Кейс В) приводило к сбору ликвидаций и ножей на суб-биржах, когда на Binance не было движения.
  * *Решение:* Строгий режим `static_leg: "TARGET"` по умолчанию. В `evaluate_pair_stability` и `evaluate_entry_v9` Кейс В категорически отвергается с причиной `CASE_C_REJECTED`. Разрешен только истинный Lead-Lag импульс Оракула (Кейс Б).
* **Мина №2 (Трение тейкера и дырявые стаканы):**
  * *Проблема:* На монетах с широким спредом (>0.05-0.10%) математический перевес мгновенно уничтожался BBO-разрывом и двойной комиссией.
  * *Решение:* Внедрен фильтр плотности стакана `StaticDetector.check_target_tick_density` с порогом `max_target_spread_ratio: 0.0003` (0.03% / 1-2 тика). Разреженные стаканы блокируются до расчета входа (`TARGET_BOOK_TOO_WIDE`).
* **Мина №3 (Слепой рыночный сброс 15s TTL & Decay Map):**
  * *Проблема:* Сброс позиции единым маркетом по истечении 15 секунд или деградации гарантированно продавливал стакан и съедал PnL.
  * *Решение:* Полноценная имплементация 4-стадийного Orderbook Hunting из `Rucheiok Bot 2.0`:
    1. **Стадия 1 (Virtual TP Hunting):** Сканирование книги заявок `find_liquidity_target` и отправка `LIMIT_IOC` в пул максимальной ликвидности у/выше виртуального тейка.
    2. **Стадия 2 (Breakeven Stage):** При откате после набора профита ($\ge 0.15\%$) бот выходит по расчетной цене безубытка с полным покрытием комиссий через `LIMIT_IOC`.
    3. **Стадия 3 (Progressive Step Extrime Close):** После 60с удержания включается ступенчатый сбор ликвидности стакана (`steps: [0, 1, 2, 3]`) ордерами `LIMIT_IOC` вместо одного удара по рынку.
    4. **Стадия 4 (Oracle Reversal Hard Protection):** Ордер `MARKET` строго изолирован и применяется исключительно при развороте поводыря Binance против позиции на $\ge 0.20\%$ (`ORACLE_REVERSAL_STOP`).
